# Audit Log Service - Testing & Test Case Document

---

## 1. QA Strategy
The quality assurance strategy for the Audit Log Service focuses on validating security boundaries, data integrity, and compliance gates (specifically the 7-year retention rule). Testing combines automated validation (unit and integration tests) with manual validation using Postman collection request cycles.

Key testing targets:
1.  **Immutability and Retention Rules**: Asserting that logs cannot be deleted or altered within the 7-year window.
2.  **Redaction Security**: Confirming that sensitive fields are completely masked.
3.  **Tenant and Scope Isolation**: Ensuring tenant admins cannot access other tenants' audit logs, and regular users can only read their own logs.
4.  **Middleware Reliability**: Confirming that HTTP logs are captured asynchronously without interrupting response delivery or throwing unhandled exceptions.

## 2. Test Cases & Verification Scenarios

### 2.1 Test Case Suite 1: Ingestion & Sanitization

#### TC-AUD-01: Automatic HTTP Logging Capture
*   **Objective**: Verify that the middleware logs standard authenticated HTTP mutations.
*   **Pre-conditions**: User is logged in as Tenant Admin.
*   **Test Steps**:
    1. Send a `POST /api/v1/workflows/definitions` request.
    2. Query `GET /api/v1/audit-logs` filtering by `action = 'CREATE'`.
*   **Expected Result**: An audit log is present containing matching metadata, user ID, tenant ID, request method `'POST'`, and response status `201`.

#### TC-AUD-02: Sensitive Payload Redaction
*   **Objective**: Verify passwords and auth tokens are masked in audit logs.
*   **Pre-conditions**: User is attempting login.
*   **Test Steps**:
    1. Send a `POST /api/v1/auth/login` request with `password: "Secret123!"`.
    2. Query the audit logs database for the login action.
    3. Retrieve the `request_body` from the matching audit log entry.
*   **Expected Result**: The `password` field in `request_body` is set to `"[REDACTED]"`.

### 2.2 Test Case Suite 2: Access & Compliance Control

#### TC-AUD-03: Tenant Isolation Boundary
*   **Objective**: Prevent cross-tenant log leakage.
*   **Pre-conditions**: Two active tenants (Tenant A and Tenant B).
*   **Test Steps**:
    1. Log in as Tenant Admin A.
    2. Request `GET /api/v1/audit-logs?tenant_id=Tenant_B_ID`.
*   **Expected Result**: The endpoint returns logs matching Tenant A's context only, ignoring the `tenant_id` query parameter for Tenant B.

#### TC-AUD-04: User Self-Log Restriction
*   **Objective**: Verify regular users can only view their own logs.
*   **Pre-conditions**: Regular User C (non-admin) under Tenant A.
*   **Test Steps**:
    1. Log in as User C.
    2. Send request to `GET /api/v1/audit-logs`.
    3. Send request to `GET /api/v1/audit-logs/my-logs`.
*   **Expected Result**: The request to `/audit-logs` returns `403 Forbidden`. The request to `/my-logs` returns `200 OK` showing only logs generated by User C.

#### TC-AUD-05: 7-Year Retention Delete Lock
*   **Objective**: Verify logs younger than 7 years cannot be deleted.
*   **Pre-conditions**: Audit log entry created 1 day ago.
*   **Test Steps**:
    1. Log in as Super Admin.
    2. Execute `DELETE /api/v1/audit-logs/:id` using the log's ID.
*   **Expected Result**: Request fails with `400 Bad Request` or `500 Server Error`, returning the message: `"Audit log cannot be deleted before 7 years retention period"`.
